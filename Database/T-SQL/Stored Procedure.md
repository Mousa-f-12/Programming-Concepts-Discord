# Stored Procedure in SQL Server — شرح هندسي مبسّط

خلينا نفهم الـ **Stored Procedure** من الصفر، ليس فقط ما هي وكيف نكتبها، بل لماذا اخترعها SQL Server، وما المشكلة التي تحلها، وكيف نفكر فيها كمبرمجين.

---

## 1. ما هي الـ Stored Procedure؟

الـ **Stored Procedure** هي مجموعة من أوامر وتعليمات T-SQL نقوم بتخزينها داخل قاعدة البيانات تحت اسم معين، بحيث نستطيع استدعاءها وتنفيذها عند الحاجة.

**بمعنى أبسط:**
بدلاً من كتابة نفس استعلامات SQL في كل مرة نحتاج فيها إلى تنفيذ عملية معينة، نستطيع تجميع هذه الاستعلامات داخل Stored Procedure واستدعاءها بالاسم فقط.

### مثال من الواقع:
تخيّل أن لديك نظام إدارة موظفين، وتحتاج إلى عرض الموظفين في عدة أماكن داخل النظام:
* شاشة عرض الموظفين.
* شاشة البحث عن موظف.
* شاشة التقارير.

بدلاً من كتابة منطق جلب الموظفين في كل مكان، يمكنك إنشاء Stored Procedure مسؤولة عن هذه العملية، ثم استدعاؤها من الأماكن التي تحتاج إليها.

---

## 2. لماذا نستخدم Stored Procedures؟

هناك عدة أسباب تجعلها مفيدة في تصميم الأنظمة:

1. **إعادة استخدام الكود (Reusability):**
   بدلاً من تكرار نفس استعلامات SQL في عدة أماكن، نكتبها مرة واحدة داخل Stored Procedure ونعيد استخدامها.
   * **الفائدة:** تقليل تكرار الكود وتسهيل صيانته.

2. **تنظيم منطق قاعدة البيانات (Encapsulation):**
   يمكنك تجميع مجموعة من العمليات والاستعلامات المرتبطة ببعضها داخل إجراء واحد. مثلاً، عملية تسجيل طلب جديد قد تتطلب:
   * إضافة الطلب.
   * إضافة تفاصيل الطلب.
   * تحديث المخزون.
   * تسجيل العملية.
   
   يمكن وضع هذه الخطوات ضمن Stored Procedure واحدة.
   * **الفائدة:** تجميع منطق العملية في مكان واحد داخل قاعدة البيانات.

3. **الأمان (Security):**
   يمكن منح التطبيق صلاحية تنفيذ Stored Procedure معينة دون منحه صلاحية الوصول المباشر إلى الجداول التي تستخدمها. مثلاً: يمكن السماح للمستخدم بتنفيذ إجراء يعرض بيانات الموظفين، دون منحه صلاحية تنفيذ استعلامات مباشرة على جدول الموظفين.
   * **الفائدة:** التحكم بشكل أفضل في الوصول إلى البيانات.

4. **الأداء (Performance):**
   يستطيع SQL Server الاستفادة من خطط التنفيذ المخزنة مؤقتاً (Execution Plan Caching) عند تنفيذ الإجراءات المخزنة. هذا قد يقلل تكلفة تحليل وتجهيز الاستعلامات عند تكرار تنفيذها.
   > **انتبه:** وجود Stored Procedure لا يعني تلقائياً أن الاستعلام أسرع من الاستعلام المكتوب مباشرة باستخدام ADO.NET. الأداء يعتمد على الاستعلام، والفهارس، وخطة التنفيذ، وطريقة التعامل مع البيانات.

---

## 3. كيف ننشئ Stored Procedure؟

لنفرض أن لدينا جدولاً اسمه `Employees` ونريد إنشاء إجراء مسؤول عن عرض جميع الموظفين:

```sql
CREATE PROCEDURE usp_GetAllEmployees
AS
BEGIN
    SELECT *
    FROM Employees;
END;
```

### دعنا نفهم الأجزاء:

| الجزء | وظيفته |
| :--- | :--- |
| `CREATE PROCEDURE` | إنشاء إجراء مخزن جديد |
| `usp_GetAllEmployees` | اسم الإجراء |
| `AS` | بداية تعريف جسم الإجراء |
| `BEGIN` | بداية مجموعة التعليمات |
| `SELECT` | الاستعلام الذي سينفذ |
| `END` | نهاية جسم الإجراء |

> لاحظ أن الإجراء أصبح محفوظاً داخل قاعدة البيانات، ولم نعد بحاجة إلى كتابة الاستعلام في كل مرة.

---

## 4. كيف نستدعي Stored Procedure؟

بعد إنشائها نستطيع تنفيذها باستخدام:

```sql
EXEC usp_GetAllEmployees;
```
أو:
```sql
EXECUTE usp_GetAllEmployees;
```
كلاهما يؤدي الغرض نفسه.

**لاحظ الفرق:**
* `CREATE PROCEDURE`: إنشاء الإجراء وتخزين تعريفه.
* `EXEC`: تنفيذ الإجراء.

---

## 5. Stored Procedure مع Parameters

هذه من أهم ميزات الإجراءات المخزنة. تخيّل أنك تريد البحث عن موظف باستخدام رقمه `EmployeeID`. بدلاً من إنشاء إجراء منفصل لكل موظف، يمكنك إنشاء إجراء يستقبل Parameter ويستخدم قيمته في الاستعلام:

```sql
CREATE PROCEDURE usp_GetEmployeeByID
    @EmployeeID INT
AS
BEGIN
    SELECT *
    FROM Employees
    WHERE EmployeeID = @EmployeeID;
END;
```

**استدعاؤه:**
```sql
EXEC usp_GetEmployeeByID @EmployeeID = 10;
```

### ماذا حدث هنا؟
1. استدعينا الإجراء.
2. أرسلنا إليه القيمة `10`.
3. استقبل الإجراء القيمة في المتغير `@EmployeeID`.
4. استخدم القيمة في شرط `WHERE`.
5. أعاد بيانات الموظف الذي يحمل الرقم `10`.

> **الفكرة المهمة:** الـ Parameter يسمح لك بكتابة إجراء عام يمكن استخدامه مع قيم مختلفة، بدلاً من كتابة استعلام جديد لكل قيمة.

---

## 6. Default Parameters

يمكنك إعطاء الـ Parameter قيمة افتراضية. مثلاً، نريد البحث عن موظف، ولكن إذا لم يرسل المستخدم رقماً، نعرض جميع الموظفين:

```sql
CREATE PROCEDURE usp_GetEmployees
    @EmployeeID INT = NULL
AS
BEGIN
    SELECT *
    FROM Employees
    WHERE EmployeeID = @EmployeeID
       OR @EmployeeID IS NULL;
END;
```

* **الاستدعاء الأول (يعرض الموظف رقم 10):**
  ```sql
  EXEC usp_GetEmployees @EmployeeID = 10;
  ```
* **الاستدعاء الثاني (يعرض جميع الموظفين):**
  ```sql
  EXEC usp_GetEmployees;
  ```

> لاحظ أن القيمة الافتراضية هنا هي `NULL`، وأننا تعاملنا معها صراحة داخل شرط `WHERE`.

---

## 7. ALTER PROCEDURE

ماذا لو أردت تعديل إجراء موجود؟ بدلاً من حذف الإجراء وإعادة إنشائه، تستطيع استخدام:

```sql
ALTER PROCEDURE usp_GetAllEmployees
AS
BEGIN
    SELECT EmployeeID, FirstName, LastName
    FROM Employees;
END;
```

**الفرق:**
* `CREATE`: إنشاء إجراء جديد.
* `ALTER`: تعديل إجراء موجود.
* وفي إصدارات SQL Server الحديثة يوجد أيضاً `CREATE OR ALTER PROCEDURE`، والذي ينشئ الإجراء إن لم يكن موجوداً، أو يعدّله إن كان موجوداً.

---

## 8. DROP PROCEDURE

إذا لم تعد بحاجة إلى الإجراء، يمكنك حذفه:

```sql
DROP PROCEDURE usp_GetAllEmployees;
```
> هذا يحذف تعريف الإجراء من قاعدة البيانات، وليس الجداول التي كان يتعامل معها أو بياناتها.

---

## 9. أين توجد Stored Procedures؟

الإجراءات المخزنة هي كائنات (**Database Objects**) داخل قاعدة البيانات. يمكنك رؤيتها من خلال المسار التالي في SSMS:

`Database` ➔ `Programmability` ➔ `Stored Procedures`

ومن المهم فهم أنها ليست ملفات مستقلة داخل مشروع C#، بل كائنات محفوظة في SQL Server نفسه.

---

## 10. كيف ترتبط Stored Procedures مع ADO.NET؟

هذه نقطة مهمة جداً بالنسبة لك كمبرمج يعمل على **C#** و **ADO.NET**. تخيّل أن لديك تطبيقاً لإدارة الموظفين؛ بدلاً من كتابة استعلام SQL داخل التطبيق، يمكنك استدعاء الإجراء المخزن:

```csharp
using SqlCommand cmd = new SqlCommand(
    "usp_GetEmployeeByID",
    connection
);

cmd.CommandType = CommandType.StoredProcedure;

cmd.Parameters.AddWithValue("@EmployeeID", 10);
```

### لاحظ هنا:
* حددنا اسم الإجراء.
* أخبرنا `SqlCommand` أن نوع الأمر هو `StoredProcedure`.
* أرسلنا قيمة الـ Parameter.

وبذلك أصبح التطبيق مسؤولاً عن إرسال الطلب، بينما SQL Server مسؤول عن تنفيذ منطق قاعدة البيانات. وهذا فصل مفيد للمسؤوليات، لكنه لا يعني أن كل منطق التطبيق يجب نقله إلى قاعدة البيانات.

---

## 11. متى نستخدم Stored Procedure ومتى لا نستخدمها؟

ليس كل استعلام يحتاج إلى Stored Procedure:

| الحالة | القرار |
| :--- | :--- |
| استعلام متكرر ومشترك بين أجزاء النظام | **مناسبة** |
| عملية تتضمن عدة خطوات مترابطة داخل قاعدة البيانات | **مناسبة** |
| عملية تحتاج إلى صلاحيات وصول محددة | **مناسبة** |
| استعلام بسيط جداً ومخصص لمكان واحد | **قد لا تحتاج إليها** |
| منطق أعمال معقد يعتمد على قواعد التطبيق | **قد يكون مكانه في Business Layer** |

> **تفكير المهندس:** لا تسأل نفسك: *"هل أستطيع وضع هذا الكود داخل Stored Procedure؟"* بل اسأل: *"هل وضع هذا المنطق داخل قاعدة البيانات سيجعل النظام أكثر تنظيماً وأماناً وأسهل في الصيانة؟"*

---

## 12. مفاهيم مهمة مرتبطة بها

هذه مفاهيم ستتعرف عليها أثناء دراستك للإجراءات المخزنة:

| المفهوم | وظيفته |
| :--- | :--- |
| `Input Parameters` | استقبال قيم من المستدعي |
| `Output Parameters` | إرجاع قيم إلى المستدعي |
| `Return Value` | إرجاع قيمة صحيحة من نوع `INT` |
| `TRY...CATCH` | التعامل مع الأخطاء |
| `Transactions` | ضمان تنفيذ العمليات المترابطة كوحدة واحدة |
| `SCOPE_IDENTITY()` | الحصول على آخر قيمة Identity أُنشئت ضمن نفس النطاق |
| `SET NOCOUNT ON` | منع إرسال رسائل عدد الصفوف المتأثرة بعد كل تعليمة |

> هذه ليست تفاصيل ثانوية؛ ستحتاج إليها عند بناء إجراءات حقيقية داخل الأنظمة.

---

## 🧠 الخلاصة الهندسية

**احفظ هذه الفكرة:**
> **Stored Procedure** = منطق SQL محفوظ داخل قاعدة البيانات، يمكن استدعاؤه وتنفيذه عند الحاجة، مع إمكانية استقبال Parameters وإرجاع نتائج.

والأهم أن تفهم تدفق العلاقة التالية:

```text
[ C# Application ] ──(يرسل طلباً ويحدد Parameters)──> [ ADO.NET: SqlCommand ]
                                                                │
                                                                ▼
[ Database Tables ] <──(قراءة / تعديل / إضافة)── [ SQL Server: Stored Procedure ]
```

**نصيحتي لك:** لا تنتقل مباشرة إلى كتابة إجراءات معقدة. أتقن أولاً `Parameters`، ثم `Output Parameters`، ثم `Return Values`، وبعدها انتقل إلى `TRY...CATCH` و `Transactions`. هذه هي الأساسات التي ستبني عليها إجراءات احترافية في مشاريعك.
